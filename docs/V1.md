# V1 — Single-agent engineering workspace

**Definition:** a desktop app and a CLI that run one agent against one repo,
safely, with a complete record, and a verification story that works even when
the repo has no tests. **No orchestration.**

**Shippable as:** an engine-agnostic agent frontend with an audit trail. A
product on its own — someone could use it and never know a multi-agent tier is
planned.

**Status:** V1.0 shipped. V1.1 half shipped.

Tier context: [ROADMAP](ROADMAP.md) · next tier: [MVP](MVP.md)

> The product is **Weave**; the code still says `berd`. Every command and path
> below is the real one. The rename is a V1.1 item.

### What landed

**Dependency rule enforced.** `protocol ← agent ← core ← cli`; desktop reads
core; nothing points back. Grep-checkable:

```bash
grep -rn "@tauri-apps\|from \"react\"\|apps/desktop" packages/ --include="*.ts"
# must return nothing
```

This is not tidiness. The eval harness has to be runnable from a script at 3am.
If that path goes through a desktop window it will not be run often, there are
no numbers, and every later tier becomes taste.

**Ledger.** Append-only `.berd/runs/<runId>/events.ndjson`, synchronous writes,
raw ACP payloads verbatim, self-ignoring via its own `.gitignore`. Earned here
instead of late, for the cost of one `appendFileSync`.

**Permission policy.** `confineToTaskDir`, matched on `kind`, every decision
logged with a reason. It was on a later list originally; auto-approve could not
survive the move to headless runs, because there is no human at a window.

**Two independent confinement boundaries**, because they catch different things:

| Boundary | Catches |
|---|---|
| `PermissionPolicy` on `toolCall.locations` | The agent's *own* tools — Claude Code's Edit, Bash — which never route through our client |
| `safeResolve` in `session.ts` | ACP-routed `readTextFile` / `writeTextFile` |

Neither is sufficient alone. That is also why `filesWritten` can be empty on a
successful fix while `filesChanged` (from git) is not.

**Engine registry.** `packages/agent/src/engines.ts` is the only file that names
an engine. Adding one is a row plus an install, not an adapter.

**Desktop app.** Three panes, session resume, config pills, collapsible tool
steps, git context.

### Acceptance ✅

`berd run --dir ./repo --prompt "..."` fixes a bug on disk with no window, and
the event log replays the turn.

```
run 20260902-181935-3rek
  session bd6e3f6c (new)
  · Read math.js
  · Edit math.js
  allow  Edit math.js — allow_always; within task cwd
  ok in 13700ms

{ "status": "ok", "filesWritten": [], "filesChanged": ["math.js"] }
```

### Debt carried out of V1.0

`codex` / `amp` / `gemini` are **declared, not verified**. Each has its own
`exports["."]` vs `bin` trap, `configOptions` vocabulary and permission quirks.
A registry row is a hypothesis until one completes a task.

*(The original debt list also said "no turn cap, no timeout, no token/cost
capture." All three landed in `f31b854` — see below.)*

### ✅ Shipped in `f31b854`

| | Where |
|---|---|
| Repeats per cell, default 3 | `eval/src/harness.ts` `runMatrix` |
| Fresh copy per cell — APFS `cp -c` clonefile, `fs.cp` fallback | `harness.ts` `copyRepo` |
| Anti-cheat: harness-owned files restored before `verify` | `harness.ts` `injectFiles`, called twice |
| Precondition check → `invalid-fixture` | `harness.ts` `runCell` |
| Caps: `maxTurns` (tool calls) + `timeoutMs`, cancel and report | `core/src/runner.ts` |
| `timeout` kept distinct from `fail` and `error` | `protocol/src/eval.ts` `CellStatus` |
| `noop-trap` fixture category | `protocol/src/eval.ts` |
| `cell.finished` ledger event | `protocol/src/events.ts` |
| Cost + context window from ACP `usage_update` | `runner.ts`, `eval.ts` |
| Median + min–max matrix, "Not scored" section | `eval/src/report.ts` |
| Sequential execution | `runMatrix` |
| Fixture paths resolved relative to the fixture file | `eval/src/load.ts` |
| Non-zero exit when anything fails | `cli/src/index.ts` |

Two design notes worth not re-deriving:

- **`maxTurns` counts tool calls, not ACP turns.** A task is a single `prompt`
  call and the agent's internal loop is invisible to us. Tool calls are the only
  runaway signal that crosses the wire.
- **`cp -c` on APFS is copy-on-write.** A 550MB monorepo costs ~12s and almost
  no disk. Node's `fs.cp` does a real byte copy. And *do not* symlink
  `node_modules` — pnpm links each workspace package into its siblings, and one
  root symlink does not reproduce that. Measured failing `check-types` on a
  pristine copy of a repo whose original passes.

### ✅ 1. The verification ladder

**The correction with the widest blast radius.** A repo with no test suite still
has verifiable behaviour. Detect the rungs, use the strongest the project
supports, and record which one.

Ordered **weakest to strongest**, so `strength` is monotonic and "use the
strongest rung available" is literally `max(strength)`:

```
1  diff-review   structural sanity: still parses, no deleted exports
2  lint          eslint, if configured
3  typecheck     tsc --noEmit, if tsconfig exists
4  build         next build / tsc, almost always available
5  boot          process starts and stays up N seconds
6  health        docker compose up --wait; GET /health → 200
7  smoke         scripted request flow
8  tests         pnpm test, if a real test script exists
```

*(Earlier drafts of this list ran strongest-to-weakest while the `strength`
field was already typed weakest-to-strongest — the two disagreed. This is the
corrected, single ordering; `rungStrength()` in
`protocol/src/verification.ts` is the source of truth.)*

```
packages/core/src/intake.ts      git? clean? which rungs exist, and why not?
packages/core/src/verify.ts      pick strongest → run → report
packages/protocol/src/verification.ts   VerificationRung, Verification, rungStrength
```

```ts
type VerificationRung = "diff-review" | "lint" | "typecheck" | "build"
                       | "boot" | "health" | "smoke" | "tests";

type Verification = {
  available: VerificationRung[];   // detected at intake
  used: VerificationRung[];        // actually run
  strength: number;                // 1 (weakest) … 8, for eval bucketing
};
```

Rules, and where each is enforced:

- **Never refuse a repo for having no tests.** `intake()` always returns at
  least `diff-review` — unconditional, no repo can fail to have it.
- **Verification strength is a first-class field** on `TaskResult`, `CellResult`
  and in the ledger (`intake.detected`, `verification.rung`,
  `verification.finished`). Summaries in `score.ts` bucket by strength before
  anything else, so a rung-8 pass and a rung-4 pass never share one pass rate.
- **A failing rung is a failure, never a reason to try a weaker one.** The
  rung is chosen from *what the project supports*, before running — never by
  falling down the ladder after a failure. Falling back would make every red
  suite look like a green `diff-review`.
- **`verify` on a `Fixture`/`TaskContract` requires `verifyRung` alongside it.**
  There is no safe default — guessing `tests` would silently promote a one-line
  `tsc --noEmit` to rung 8. The loader (`eval/src/load.ts`) throws on a fixture
  that violates this.
- For greenfield, `expectRungAtLeast` is the acceptance test: does the finished
  work reach at least this rung, not just "did `diff-review` pass on an empty
  directory" (which it always does, trivially).
- `berd intake` (now `weave intake`) inspects a repo's ladder without running
  an agent — useful as a to-do list: each missing rung prints why.

### ✅ 2. Twelve fixtures, not two

**4 bugfix · 2 feature · 2 refactor · 2 greenfield scaffold · 1 no-test repo ·
1 noop-trap** — all in `packages/eval/fixtures/`.

| Fixture kind | Why it is in the set | Verified at |
|---|---|---|
| bugfix ×4 (`calc`, `parser`, `cart`, `dates`) | The bread-and-butter case | `build` (4) |
| feature ×2 (`inventory`, `stats`) | Adding code is a different failure shape from fixing it | `build` (4) |
| refactor ×2 (`money`, `orders`) | `filesChanged` is large and correctness is subtle | `build` (4) |
| **greenfield scaffold ×2** (`greenfield-wordcount`, `greenfield-notes-api`) | Verify at rungs 4 and 7. The path the target user actually runs first | `build`(4) / `smoke`(7) |
| **no-test repo ×1** (`feed-server`) | Proves the ladder works with zero fixture-supplied `verify` — ladder auto-picks `boot` | `boot` (5) |
| **noop-trap ×1** (`calc-fixed`) | A prompt describing a bug that is not there. The only fixture that catches false positives | `build` (4) |

None of the 12 use a unit-test framework as the gate. Every fixture is scored
by a real project artifact — a build script, a boot check, a smoke script —
that imports the code under test and fails loudly on the actual bug. That was
a deliberate call: a "test file" living in the fixture repo is one more thing
an agent could edit to cheat, and it doesn't read as differently from
`build.mjs`/`smoke.mjs` in the anti-cheat story below — both are covered by
`readOnlyPaths` and restored from pristine the same way.

All twelve preconditions were dry-run (no agent call) and confirmed correct —
each bugfix/feature/refactor fixture's build gate fails for the actual seeded
bug, `calc-fixed` already passes, and both greenfield fixtures correctly start
below their `expectRungAtLeast`. One real cell (`calc-bugfix`, haiku, 1 repeat)
was run end to end through the full harness: 1/1 pass, scored at `build (4)`,
`readOnlyPaths` held.

### ✅ 3. Three fields documented as enforced, read by nothing

All three closed.

| Field | Was | Now |
|---|---|---|
| `Fixture.readOnlyPaths` / `TaskContract.readOnlyPaths` | Nothing read it | Enforced twice: `confineToTaskDir` rejects a tool call whose `locations` match (mutating kinds only — reads are allowed, so the agent isn't left guessing what the tests assert); `session.ts`'s `safeResolve` rejects an ACP-routed write to the same paths; the eval harness restores them from the pristine source repo before verifying, on top of both |
| `TaskContract.allowedPaths` | Nothing read it | **Still not enforced — correctly.** An allow-list is only meaningful once each task owns a worktree; narrowing lands at [MVP.1](MVP.md), as originally planned |
| `Fixture.commit` | Nothing read it, and `copyRepo` deletes `.git` so a post-copy check is structurally impossible | Checked against the *source* repo's HEAD, before the copy (`eval/src/harness.ts` `checkCommit`). A mismatch is `invalid-fixture`, never a silent pass |

The dangerous half of `readOnlyPaths` is now real: a tool call the policy
rejects never reaches the file, and an ACP write that slips past the policy
(no `locations` reported) is caught a second time in `session.ts`. Restore is
now the third layer, not the only one.

### ✅ 4. Registry hygiene for a non-Claude engine — partial

Probed `codex` and `gemini` directly: spawn the process, send a raw ACP
`initialize` over stdio. That handshake is answered before any model call, so
it needs no API key.

- `codex`'s row named a **deprecated** package (`@zed-industries/codex-acp`) —
  it refuses to install. Replaced with its successor,
  `@agentclientprotocol/codex-acp`; `binName` still matches (`codex-acp`).
- `gemini`'s row was already correct: the binary resolves, `--experimental-acp`
  is accepted, and the process replies over the ACP wire. It failed on a
  Google account-tier error (`IneligibleTierError`) before a task could run.

**What this does not close:** actually completing a task on either engine
needs an API key this environment doesn't have. The registry rows are now
confirmed-real packages with confirmed-correct `binName`s — a smaller claim
than "verified end to end," and the honest one. See [FINDINGS](FINDINGS.md).

### ✅ 5. Rename `berd` → `weave` — orchestrator scope

Done for the orchestrator: `@berd/*` → `@weave/*` in every package, the CLI
binary `berd` → `weave`, `.berd/` → `.weave/` (default runtime dir, git-ignore
comments, ledger paths), `BerdEvent`/`BerdEventType` → `WeaveEvent`/
`WeaveEventType`, `berdDirFor`/`berdDir` → `weaveDirFor`/`weaveDir`. Verified:

**Deliberately not touched:** `apps/desktop`'s own product identity —

"my-berd-app"` is the same call.

## Target types — shipped as written, plus `expectRungAtLeast`

```ts
type Fixture = {
  id: string;
  kind?: "existing" | "greenfield";  // defaults to existing
  repo?: string;                     // absent for greenfield
  commit?: string;                   // checked against source HEAD before the copy
  prompt: string;
  verify?: string;                   // explicit command, else the ladder decides
  verifyRung?: VerificationRung;     // REQUIRED alongside verify — no safe default
  readOnlyPaths?: string[];          // enforced by the policy AND restored from pristine
  expectFail: boolean;               // verification MUST fail before the run
  expectRungAtLeast?: VerificationRung; // greenfield: the rung the result must reach
  category: "bugfix" | "feature" | "refactor" | "scaffold" | "noop-trap";
};

type CellResult = {
  fixtureId: string; configId: string; repeat: number;
  status: CellStatus;             // pass | fail | timeout | error | invalid-fixture
  verification: Verification;     // which rung actually validated this
  wallMs: number; turns: number; filesChanged: string[];
  contextUsed?: number; contextSize?: number; costUsd?: number;
};
```

The cell order is the whole anti-cheat story, and every step is now real:

```
copy fixture repo to a temp dir       ✅  never run twice in the same tree
check the commit pin (before copy)    ✅  copyRepo deletes .git — too late after
intake: detect available rungs        ✅  core/src/intake.ts
assert precondition                   ✅  verification fails when expectFail
core.runTask                          ✅  readOnlyPaths enforced by the policy
restore readOnlyPaths from pristine   ✅  THEN verify — belt AND suspenders
run the ladder, record every rung     ✅  verification.rung + verification.finished
git diff → filesChanged               ✅  never filesWritten — see FINDINGS
append cell.finished to the ledger    ✅  carries strength + used rungs
```

## Five things that decide whether the numbers mean anything

1. **Repeats ≥ 3 per cell.** ✅ Report `passed/total`, median, min–max.
   Retrofitting repeats invalidates every baseline collected before it.
2. **Fresh copy per cell.** ✅ `git checkout .` leaves untracked files;
   `git clean -fdx` takes `node_modules`. Copy to temp, run, discard — which
   also pulls MVP's isolation forward for free.
3. **Cheat resistance.** ✅ Restore *and* `readOnlyPaths` enforcement, both live
   — two independent defences, neither trusted alone.
4. **Bucket by verification strength.** ✅ `summarize()` groups by
   fixture × config × strength before computing anything; the report is
   sectioned by rung, strongest first.
5. **Sequential execution.** ✅ Wall clock is a metric; parallel cells contend
   for CPU and rate limits and stop comparing. Parallelism is the thing being
   measured, not the thing to measure with.

And the meta-rule, learned the expensive way in [FINDINGS](FINDINGS.md):

> **A benchmark's first surprising result is usually a bug in the benchmark.**
> The number was produced by the harness, so it is evidence about the harness
> before it is evidence about the model.

## Exit criteria for V1

`weave eval` runs **12 fixtures × ≥2 configs × ≥3 repeats** unattended and
prints, **per verification rung**, pass rate, median wall clock, tokens, cost
and files changed.

**Mechanically satisfied:** the harness accepts and correctly scores all 12
fixtures (dry-run confirmed on every precondition, one real cell run end to
end), and `renderMatrix` sections its output by rung. **Not yet run:** the full
72-cell matrix (12 × 2 configs × 3 repeats) — that is the actual baseline
number, and it is real API cost and wall-clock time, not a wiring question.

That table is the baseline every later tier is measured against. Without it,
[MVP](MVP.md)'s three-arm experiment has nothing to compare to and the
parallelism decision reverts to taste.

## What V1 deliberately does not do

No pool, no worktrees, no scheduler, no planner, no context model, no routing.
One agent, one repo, one task at a time.

If a V1 problem looks like it needs two agents, the answer at this tier is a
better prompt or a smaller task — not a scheduler. The tier rule holds: V1 has
to be usable as-is, or the ladder is fiction.
