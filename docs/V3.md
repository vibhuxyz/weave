# V3 — Production-grade autonomous engineering platform

**Definition:** it decides how much to spend, recovers from its own failures,
and knows when to ask a human.

**Shippable as:** something you can leave running unattended on real work.

**Status:** not started. Every part of V3.1 is a **reader over data collected at
[V1](V1.md) and [MVP](MVP.md)** — it cannot be built earlier, and it becomes
straightforward once the ledger has history.

Tier context: [ROADMAP](ROADMAP.md) · previous: [V2](V2.md) · next: [V4](V4.md)

---

## What forces this tier

[V2](V2.md) can run a large repo safely. It still cannot answer three questions
a human currently answers:

| Question | V2's answer | V3's answer |
|---|---|---|
| Which model for this task? | Whatever the config says | Measured history per task category |
| How much is this allowed to cost? | `maxTurns` and `timeoutMs`, per task, fixed | A budget ceiling, enforced |
| It failed — now what? | Report it | Classify it, then respond |

The third is the one that makes "leave it running" possible.

## V3.1 — routing, budgets, adaptive scale

```
packages/core/src/routing.ts    task profile + measured history → engine/model
packages/core/src/budget.ts     per-task token, cost, runtime ceilings
packages/core/src/scale.ts      worker count 2 → 4 → 6 → 3 → 1
packages/core/src/critpath.ts   prioritise the path that gates completion
packages/core/src/decide.ts     heuristic → measured parallel-benefit estimate
```

### Route by measured evidence, not taste

`routing.ts` reads the eval matrix and the ledger, not a preference. The input
is a task profile (category, size, verification rung available) and the output
is an engine plus model.

This is why [V1.1](V1.md) has to verify a non-Claude engine end to end. A
registry row is a hypothesis; routing between hypotheses is theatre.

### The fallback chain

```
primary → secondary on failure → supervisor → human
```

A cheap model generating with a strong model reviewing is often cheaper than a
strong model doing both.

**Claim it only once the harness shows it.** That sentence is the whole
discipline of this tier — it is exactly the shape of the Redis finding in
[FINDINGS](FINDINGS.md), where measuring first stopped an optimisation from
being installed to fix a data-loss bug.

### Budgets

Per-task token, cost and runtime ceilings. Not a dashboard — **a denial.** A
budget that reports overspend after the fact is a report, not a budget.

V1's `maxTurns` / `timeoutMs` are the primitive version of this: caps that
cancel. V3 makes the ceiling a function of the task rather than a constant.

### `decide.ts` graduates

```
parallel benefit = serial time − parallel time − coordination overhead
```

At [MVP](MVP.md) every term was unmeasured, so `decide.ts` used a path-disjoint
heuristic. Here the ledger has medians per task category, so the formula finally
has inputs. **The formula does not change — the inputs arrive.**

### Adaptive scale

Worker count moves `2 → 4 → 6 → 3 → 1` over a run, driven by the ready set and
the critical path — not by a constant. `critpath.ts` prioritises the path that
gates completion, so the last task does not start last.

> **Scale worker count to actual workload.**

## V3.2 — supervisor, checkpoints, policy, replay

```
packages/core/src/supervisor.ts   continue · wait · retry · replan · escalate
packages/core/src/checkpoint.ts   input snapshot · worktree · diff · context ver
packages/core/src/policy.ts       auto / approve / deny, by risk class
packages/core/src/replay.ts       reader over the ledger — small, it exists
```

### The failure taxonomy drives everything

**Never blindly retry.** Classify first, then respond:

| Failure | Response |
|---|---|
| Network | Retry |
| Environment | Recreate the sandbox |
| Missing dependency | Wait |
| Bad implementation | Replan |
| Conflict | Reschedule |
| Ambiguity | Ask a human |
| Dangerous operation | Require approval |

A blind retry turns a bad plan into the same bad plan, three times, at triple
the cost. The taxonomy is what makes `RECOVERABLE` a meaningful state rather
than a synonym for "try again".

`RECOVERABLE` is set **by the supervisor after classifying**, never by the
worker. The worker does not know why it failed.

### Checkpoints

Input snapshot · worktree · diff · context version. Enough to resume a task
rather than restart it, and enough to answer "what did this worker actually see"
after the fact.

### Policy

`auto / approve / deny`, by risk class. This is where the permission story from
[V1](V1.md) grows a second axis: V1 asks *where* (inside the task dir?), V3 asks
*how dangerous* (a migration against live data is not an `npm install`).

### Replay

Mostly a reader over the ledger, which already exists — so this is smaller than
it sounds. That is the dividend from writing every raw ACP payload verbatim at
V1.0.

## V3.3 — security and the full verification pipeline

### Sandbox policy per worker

Filesystem restrictions, network policy, secret isolation, CPU/RAM limits.
**Production DB, SSH keys and cloud credentials denied by default.**

> **Infrastructure is the security boundary, never the LLM.**

Non-negotiable, and already true in the two-boundary design at V1.0. This tier
extends it from *paths* to *resources*.

### The verification ladder extends upward

[V1](V1.md)'s eight rungs were about "did it work". These are about "is it safe
to ship":

```
security scan · dependency audit · performance · migration validation
```

Each applied **only where the project model says it applies.** A static site
does not get migration validation. That gating is what stops the pipeline from
becoming ceremony.

## Exit criteria for V3

Two, both measured:

1. **Measured routing beats a fixed strongest-model config on cost at equal
   pass rate**, across ≥12 fixtures × ≥3 repeats.
2. **A killed worker mid-run is detected, released, resumed or replanned** — and
   the whole sequence is legible in the ledger afterwards.

Point 2 is the one that earns "leave it running unattended". Kill a worker on
purpose; if you cannot reconstruct what happened from the ledger, the tier is
not done.

## What V3 deliberately does not do

**No remote workers.** Everything here assumes the orchestrator can watch its
own children exit — `pool.ts` tracks processes, and a dead child fires `exit`.
Leases, heartbeats and fencing tokens are ceremony between a parent and its own
children.

They stop being ceremony at [V4](V4.md), and not before.

**No Postgres, no Redis.** Still one user, one machine. SQLite for task state,
`sqlite-vec` or a flat file for the index. Design the interfaces — every write
carries a `leaseId`, every worker has an id independent of its process — and
implement none of it yet.
