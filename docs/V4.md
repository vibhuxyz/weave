# V4 — Distributed / team / cloud platform

**Definition:** workers the orchestrator cannot see die, and more than one human.

**Status:** not started, and deliberately far away. Realistically **a company,
not a milestone.**

Tier context: [ROADMAP](ROADMAP.md) · previous: [V3](V3.md)

---

## The one condition that unlocks it

> **Implement none of this until a worker runs somewhere you cannot watch it
> exit.**

That is the whole gate. Through [V3](V3.md), the orchestrator spawns its own
children on its own machine. A dead child fires `exit`. Heartbeats between a
parent and its own children is ceremony — you already have the truth.

The moment a worker runs on another machine, that stops being true. You cannot
distinguish *slow* from *dead*, and every mechanism below exists to answer that
one question.

## What the tier contains

| Area | What it means |
|---|---|
| Remote workers | Execution off the orchestrator's machine |
| Real leases with expiry | A claim that dies on its own if nobody renews it |
| Fencing tokens | The answer to "the worker you declared dead just woke up and wrote" |
| Worker registration | A worker announces itself instead of being spawned |
| Cross-machine scheduling | The DAG's ready set spans hosts |
| Postgres + pgvector | Shared state that outlives one process |
| Redis | Queues and locks across machines |
| Multi-user projects, shared runs | More than one human on one project |
| Org policy | Permissions that are not one person's preference |

## Storage — what moves, and what does not

Local through V3. This is the table from [ROADMAP](ROADMAP.md) §3.5, restated
here because V4 is where the right-hand column finally applies:

| Need | Through V3 | V4 |
|---|---|---|
| Event history | `.berd/runs/*/events.ndjson` (built) | same, plus shipping |
| Task / run state | SQLite `.berd/state.db` | Postgres |
| Worker liveness | in-process registry + child `exit` | heartbeats + leases + fencing |
| Locks / ownership | in-memory map in `core` | Redis |
| Vector index | `sqlite-vec` or a flat file | pgvector |

Note that the **ledger does not change shape**. It gains shipping — the events
go somewhere central — but the format, the append-only rule and the raw-payload
rule are the same ones earned at V1.0. That is the payoff for having built it
first.

The reason none of this arrives early is recorded in [FINDINGS](FINDINGS.md):
one user, one machine, no shared state, no repeated expensive read. Redis was
measured and had nothing to do. **Measure before adding a component.**

## The seams to design early, and implement late

Two, and they cost almost nothing to honour from V1 onward:

1. **Every write carries a `leaseId`.** Even when the lease is always valid and
   nothing checks it. Retrofitting an ownership token into every write path
   later is the expensive version.
2. **Every worker has an id independent of its process.** A PID is not an
   identity — it is reused, and it is meaningless on another host. `taskId` is
   already in every ledger event; worker identity is the same discipline one
   level down.

Design them now. Implement the machinery that reads them only when a worker runs
somewhere you cannot watch it exit.

## The rule that protects the tiers below

> **Do not let V4's requirements leak into [V2](V2.md).**

This is the most likely way the ladder breaks. Every V4 mechanism has a
plausible-sounding early justification:

| The tempting argument | Why it is wrong before V4 |
|---|---|
| "Leases are just good practice" | A lease answers *is this worker dead*. You already know — the child fired `exit`. |
| "Postgres now saves a migration later" | It also adds a service, a connection pool and a failure mode to a single-user desktop app. |
| "Redis for the event bus" | The bus is a reader over the ledger. There is no second consumer to decouple from. |
| "Design for scale early" | Scale is the one thing that is genuinely cheap to add *after* you can measure the bottleneck. Correctness is not. |

Each of those arguments is answered by the same sentence: **measure before
adding a component.** Nothing in V1–V3 has produced a measurement that
justifies any of it, and the profiling run in [FINDINGS](FINDINGS.md) actively
produced the opposite.

## Why this is honestly a company

Remote execution means: a control plane, worker images, credential distribution,
network policy between hosts, per-tenant isolation, billing, and an on-call
story for when the scheduler wedges at 3am.

[V1](V1.md) and [MVP](MVP.md) are the product. [V2](V2.md) and [V3](V3.md) make
it good. V4 is a different kind of undertaking, and naming it that way is what
keeps it from quietly setting the requirements for the tiers that ship.
