# V2 — Intelligent coordinated multi-agent system

**Definition:** agents that share knowledge, avoid each other by construction,
and receive only the context they need.

**Shippable as:** the version that works on large real repos rather than clean
fixtures. [MVP](MVP.md) parallelises; **V2 makes parallelising safe on a
monorepo.**

**Status:** not started. Gated on MVP's three-arm experiment — if arm B wins,
most of this tier is unnecessary and should not be built.

Tier context: [ROADMAP](ROADMAP.md) · previous: [MVP](MVP.md) · next: [V3](V3.md)

---

## What forces this tier

MVP's isolation is per-worktree and its conflict avoidance is "the planner gave
them disjoint paths". Both assumptions break on a real monorepo:

| MVP assumption | How a monorepo breaks it |
|---|---|
| The planner knows which files a task touches | It doesn't. It guessed from the prompt. |
| Disjoint file sets mean no conflict | Two workers in the same module with no file collision still break an API contract. |
| Dependencies are known at plan time | Half of them are discovered mid-run. |
| The whole repo fits in context | It doesn't, and stuffing it in degrades adherence. |

V2 answers each: ownership (module-level, not just file-level), dynamic
dependencies, and a project model that makes retrieval possible.

## V2.1 — ownership, events, dynamic dependencies

> **Built, 2026-09-24.** `packages/core/src/coordination/` turns the static DAG into a living task
> graph. Employees publish structured events (never free-form chat): a ` ```weave-event ` block in
> an engine's message stream, parsed from the ledger, or `coordination.publish()` for in-process
> workers. The `Coordinator` versions artifacts and contracts, routes each event to the inboxes of
> the tasks that depend on it, and logs every event as `coordination.event` in the run ledger.
> **A dependent starts as soon as its producer has published every `requiredOutputs` entry**, not
> when the producer finishes (`scheduler.nextStep(tasks, states, availableOutputs)`). Ownership is
> claimed at launch from `allowedPaths` plus `TaskContract.owns` (file, directory, module, symbol,
> api, event, schema, resource); an overlapping claim leaves the task `BLOCKED` until the owner
> settles. `dependency.blocked` adds a dependency mid-run: the producer is the named task, then the
> resource owner, then whoever published or declared the output. A cycle or a missing producer
> becomes `escalation.created`. Updates that arrive while an engine employee works become its next
> prompt turn (at most 2 rounds). A consumer ends `failed` if its producer failed, or if it built
> against an artifact version that was later replaced. Tests: `coordination/coordination.test.ts`,
> `pool/coordination.test.ts`, `run-plan/engine-worker.test.ts`.

```
packages/core/src/ownership.ts    path + module claims, in-memory
packages/core/src/bus.ts          typed events over the existing ledger
packages/core/src/state.ts        active tasks, claims, discoveries, versions
packages/core/src/scheduler.ts    DEPENDENCY_DISCOVERED rewrites the DAG
```

### Ownership is file-level *and* module-level

Two workers in the same module with no file collision can still break an API
contract. File claims alone will not catch that.

**Enforce ownership outside the LLM.** Never rely on agents to avoid conflicts
themselves — that is a rule, not a preference, and it is the same principle as
"infrastructure is the security boundary, never the model".

A task that cannot get a claim goes `BLOCKED`, not `FAILED`. Different states
demand different responses.

### The event bus is a reader over the ledger

Not a second infrastructure system. Every event is **already written** to
`.berd/runs/<runId>/events.ndjson`; this adds subscription over it.

That is the whole point of having earned the ledger at V1.0 — the bus costs a
subscriber, not a broker. See the storage table in [ROADMAP](ROADMAP.md) §3.5
for why Redis stays out until [V4](V4.md).

### Dynamic dependencies

`DEPENDENCY_DISCOVERED` rewrites the DAG mid-run, without a restart. A worker
that finds it needs an output nobody planned for is the normal case on a real
repo, not an exception.

The response is still *split the task, don't stop it* — the same correction that
makes MVP's parallelism pay.

## V2.2 — project intelligence

> **Built (deterministic layer), 2026-09-24.** `packages/core/src/context/` — no model calls:
> scan (`git ls-files`, else a sorted walk) → workspaces and stack from manifests, workspace globs
> and tsconfig `paths` → TypeScript compiler parse per file (symbols incl. class methods, imports
> with bindings, calls, HTTP routes, Next.js route files, contract objects `{ method, path }`,
> events) → dependency graph (relative, alias and workspace-package resolution; call edges through
> imports and re-exports) → git history (last 100 commits) → architecture layers per workspace.
> `buildProjectModel()` returns the `ProjectModel`; parsed modules are cached by content hash in
> `.weave/context/modules.json`, so a rebuild re-parses only changed files (this repo: 1.6 s cold,
> 0.55 s warm, 1,118 modules). `queryProject(model, request)` answers "Change the seller payout API"
> with the application, files, symbols, imports/dependents/callers/callees, APIs and contracts,
> events, recent commits and verification (tests importing those files + workspace scripts) — see
> `context/context.test.ts`. `planAndRun()` injects `renderProjectContext()` (8 KB budget) into the
> planner prompt for existing projects. The parser is the `typescript` compiler, not ts-morph.
>
> Also built: `impact/` — `analyzeImpact(model, { files, symbols })` walks reverse imports and
> reverse calls (3 hops) to dependents, callers, affected APIs, tests and workspaces.
> `update/` — `updateProjectModel(previous)` re-parses changed files only and returns revision n+1
> with a delta: files and symbols added / removed / modified (per-symbol source hash) and their impact.
> `docs/` — `generateProjectDocs()` writes `architecture.md`, `apis.md`, `data-flow.md` (route →
> handler → resolved calls → events). `vectors/` — local hashed TF-IDF vectors over symbol, file and
> API names (words + character trigrams, cosine), used when exact terms match nothing. These are not
> neural embeddings: that needs an embedding provider and a store such as sqlite-vec, which would be
> a new dependency. Calls through `const x = new Class()` now resolve to `Class.method`.

```
packages/core/src/context/
  scan.ts        deterministic first: manifests, tsconfig, routes, schema, CI
  model.ts       services · modules · APIs · entrypoints · deps
  graph.ts       ts-morph: imports, calls, routes
  docs.ts        generated architecture.md, apis.md, data-flow.md
  index.ts       embeddings (sqlite-vec), retrieval + ranking
  update.ts      diff → changed symbols → callers → v(n+1)
  retrieve.ts    task → assembled context under a token budget
  impact.ts      which files does this change touch?
```

### Deterministic analysis first

Manifests, tsconfig, routes, schema, CI config — all of it is readable without a
model. The LLM is used **only where reasoning is genuinely required.**

That is what keeps context generation affordable on a large repo. A model call
per file does not scale; a parse per file does.

### Structured model = truth, vectors = retrieval

The distinction matters and is easy to get backwards.

> RAG cannot answer *"which service owns `/api/payment`"*.

That is a graph lookup against a structured model. Embeddings are for *finding
plausibly relevant code to read*, not for answering structural questions. Build
the model; use vectors to search it.

### Incremental updates, never full rescan

```
diff → changed symbols → their callers → v(n+1)
```

A full rescan per edit would dominate cost. The update walks outward from what
actually changed.

### Context is versioned, and deltas are prompt turns

A delta arrives **between turns, as a prompt turn** — never as a mid-turn patch.
Where a delta invalidates work already done: cancel that task and re-run it.

The Context Updater is a **privileged system worker**, not a free-running
documentation agent. It has write access to the model that every other worker
reads; that asymmetry is deliberate.

> **Share project knowledge, not write access.**

### Retrieval under a token budget

`retrieve.ts` assembles context for one task under an explicit budget. Combined
with MVP's tool-output compression, this is what keeps a retrying worker from
eating its own window.

## V2.3 — the full dashboard

Plan, workers, context version, tokens, cost, done count. Per-task drill-down:
overview · terminal · files · diff · events · tests · context.

**The user should not see the distributed-systems machinery.** Claims, DAG
rewrites, context versions and lease ids are how it works, not what it is for.
The dashboard shows work and money, and hides the scheduler.

Builds on MVP.3's lanes, which already keyed the transcript by `taskId`.

## Exit criteria for V2

All five, measured — not judged:

1. **`impact.ts` names the affected files correctly** for a known change set.
2. **Context v(n) → v(n+1)** after an edit touches only affected areas, and
   completes in seconds.
3. **Two tasks contending for one file resolve without corruption.**
4. **A discovered dependency reorders a run without a restart.**
5. **The [V1](V1.md) fixture matrix improves on MVP numbers** for large-repo
   fixtures — at equal verification rung.

Point 5 is the one that decides whether the tier was worth building. The other
four are mechanisms; that one is the outcome.

---

## What V2 deliberately does not do

No routing, no budgets, no supervisor, no adaptive worker count. Those all read
measured history, and V2 is where the history starts being rich enough to be
worth reading — but reading it is [V3](V3.md).

No Postgres, no Redis, no pgvector. `sqlite-vec` or a flat file is the vector
index at this tier. One user, one machine, no shared state — the reason is in
[FINDINGS](FINDINGS.md) and it has not changed.
