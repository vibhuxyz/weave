# Database conventions

Default: Postgres with Prisma or Drizzle. Redis for cache, locks, rate limits.

---

## 1. Naming

| Thing | Rule | Example |
| :--- | :--- | :--- |
| Table | snake_case, plural | `users`, `order_items` |
| Column | snake_case | `created_at`, `user_id` |
| Primary key | `id` | UUIDv7 |
| Foreign key column | `<singular>_id` | `order_id` |
| Join table | both names, alphabetical | `products_tags` |
| Boolean | `is_` / `has_` | `is_active` |
| Index | `idx_<table>__<cols>` | `idx_orders__user_id__created_at` |
| Unique | `uq_<table>__<cols>` | `uq_users__email` |
| Check | `ck_<table>__<rule>` | `ck_payments__amount_positive` |

* **DB-01 MUST** — ORM fields are camelCase in TS, mapped to snake_case columns
  (`@map` in Prisma, `casing: 'snake_case'` in Drizzle).

## 2. Types

* **DB-02 MUST** — money: `bigint` minor units or `numeric(p, s)`. Never `float`, `real`,
  `double`, or `money`. Store `currency` next to the amount.
* **DB-03 MUST** — time: `timestamptz` in UTC. Every table has `created_at`; mutable tables
  have `updated_at`.
* **DB-04 SHOULD** — enums as `text` + `CHECK` (easier to change than Postgres `ENUM`).
* **DB-05 MUST** — `NOT NULL` by default. A nullable column needs a reason.
* **DB-06 SHOULD** — `jsonb` only for data you never filter or join on. If you query it, it
  becomes columns.
* **DB-07 MUST** — emails stored lowercased or with `citext`, with a unique index.

## 3. Integrity

* **DB-08 MUST** — relationships have foreign keys. Rules the DB can enforce (unique, positive
  amount, valid status) are constraints, not only app code.
* **DB-09 MUST** — every foreign key column has an index.
* **DB-10 SHOULD** — `ON DELETE` is chosen on purpose: `RESTRICT` by default, `CASCADE` only for
  true children (order → order_items).

## 4. Money and audit data

Think of a Paytm passbook: you never edit a past line, you add a new one.

* **DB-11 MUST** — balance changes are rows in an append-only ledger table. Wrong entries are
  fixed with a reversing entry, never `UPDATE`/`DELETE`.
* **DB-12 MUST** — a cached balance changes in the same transaction as its ledger row, and a
  test checks they match.
* **DB-13 SHOULD** — soft delete (`deleted_at`) only where users expect "undo" or law needs
  retention. Financial and audit tables are never deleted at all.

## 5. Transactions and concurrency

* **DB-14 MUST** — no network calls (HTTP, queue, email, Redis) inside a DB transaction.
  Write an outbox row; publish after commit.
* **DB-15 MUST** — pick a concurrency tool on purpose and name it in a comment:
  * unique constraint — duplicates (idempotency keys, emails)
  * `SELECT ... FOR UPDATE` — one row, short critical section (stock count)
  * optimistic `version` column — edits that rarely clash (profile, settings)
  * `SERIALIZABLE` + retry on `40001` — invariants across many rows (balances)
* **DB-16 SHOULD** — transactions stay short (~tens of ms).
* **DB-17 MUST** — idempotency keys have a unique index: `uq_<table>__user_id__idempotency_key`.

## 6. Queries

* **DB-18 MUST** — select only the columns you need in hot paths.
* **DB-19 MUST** — no N+1. Load relations with a join or one `IN` query.
* **DB-20 MUST** — pagination is keyset: `where (created_at, id) < ($1, $2) order by created_at desc, id desc`.
* **DB-21 MUST** — every hot query has an index matching `where` + `order by`. Paste `EXPLAIN` in
  the PR when adding one.
* **DB-22 MUST** — raw SQL only with parameters (`sql` tag / `$queryRaw` template). Never string
  concatenation.

## 7. Migrations

* **DB-23 MUST** — generated by the ORM tool, then read by a human before merge.
* **DB-24 MUST** — a merged migration is never edited. Fix forward.
* **DB-25 MUST** — breaking changes go expand → migrate → contract over separate deploys:
  add new column → write both + backfill → read new → drop old.
* **DB-26 MUST** — one purpose per migration, named for it: `0014_add_orders_status`.
* **DB-27 MUST** — indexes on tables with data use `CREATE INDEX CONCURRENTLY`.
* **DB-28 MUST** — migrations run in CI against a real Postgres before merge.
* **DB-29 SHOULD** — big backfills run as a batched job, not inside the migration.

## 8. Redis

* **DB-30 MUST** — keys are `app:resource:id:field`: `shop:cart:u_42`, `shop:ratelimit:ip:1.2.3.4`.
* **DB-31 MUST** — every cache key has a TTL. No key lives forever by accident.
* **DB-32 MUST** — Redis is never the only copy of data you cannot rebuild.
* **DB-33 MUST** — locks have a TTL and a fencing token/owner check on release.
* **DB-34 SHOULD** — cache invalidation is written next to the write that makes it stale.

## 9. Multi-database (Postgres + Mongo, etc.)

* **DB-35 MUST** — one database is the source of truth for each fact. The other holds a copy
  updated by events.
* **DB-36 MUST** — cross-database writes use outbox + idempotent consumers or a saga with
  compensation. Never assume two writes both succeed.

## 10. Local, test, and production data

* **DB-37 MUST** — `pnpm db:seed` is idempotent and gives a usable app (test users, sample data).
* **DB-38 MUST** — integration tests use a real database (Docker/Testcontainers), not mocks or
  SQLite, with a fresh schema or rolled-back transaction per test.
* **DB-39 MUST** — no real user data in dev or test databases.
* **DB-40 MUST** — production has automated backups and a restore that has been tested at least once.
